# 从零认识我们的 NDS 调度方案

## 先用一分钟了解我们解决什么

计算设备处理数据之前，必须先把数据从存储设备搬到计算设备的内存。数据分散、大小不一、内存空间有限，而且多个搬运任务会争用同一条通道。这道题要求我们决定：哪些数据一起搬、走哪条路线、怎样安排依赖，以及哪些数据值得额外缓存。

我们的方案是一个在线调度程序。它只根据已经到达的请求、当前资源状态和历史访问记录作决定。主办方提供模拟器，负责计算这些决定实际要花多久、是否违反资源限制，以及最终得分。

交付的是可以运行和验证的赛题调度算法，不是对真实 SSD 或 NPU 驱动的改造。报告中的性能数值来自官方确定性模拟器。

## 认识六个词就能继续阅读

| 名称 | 通俗含义 | 在本题中的作用 |
| --- | --- | --- |
| SSD | 存放数据的固态硬盘 | 读取的起点，多张卡共享其带宽 |
| HBM | 计算设备上的高速内存 | 数据最终到达的位置，也有一部分临时空间 |
| DDR | 主机内存 | 可作为搬运中转站；与 HBM 临时池分别计容量 |
| IOCB | 一份读取任务单 | 描述读哪个位置、读多少，以及目标设备 |
| iov | 一个目标内存片段 | 一份任务可能要写入多个不相邻片段 |
| Trace | 按时间排列的请求记录 | 模拟器用它重现整个工作过程 |

这里的 KVCache 内存池是另一块用于重复访问的缓存空间。缓存键是“设备、SSD 起点、长度”，不是只看文件位置；两份读请求只有键一致，才可能共享这份缓存。

## 为什么不能所有数据都走同一条路

可以把 SSD 看成仓库，把目标 HBM 看成工作台。搬货有三条路线：

| 路径 | 数据怎么走 | 适用条件和代价 |
| --- | --- | --- |
| DIRECT | SSD → 目标 HBM | 路线短，但每个实际读取和写入片段都要满足 512 字节对齐 |
| AGGREGATE | SSD → 临时 HBM → 目标 HBM | 可以先合并读取，再在设备内分发；占用临时 HBM、任务槽位和 D2D 复制资源 |
| FALLBACK | SSD → DDR → 目标 HBM | 通过主机内存中转；占用 DDR 和 H2D 复制资源 |

“对齐”可以理解为按固定格子取货：起点和长度都落在 512 字节格子边界上。数据不对齐时，可能需要多读首尾一点，再只把真正需要的部分复制到目标。不能把多读的数据写到无关位置。

合并也不是越多越好。大批合并能减少调用，但可能长期占住任务槽位，让后面的批次排队。切得太碎则会增加命令数，还可能产生几字节的小尾块。因此，我们同时考虑块大小、分组边界和路径。

## 什么叫“更好的方案”

赛题用综合成本 J 衡量一个完整 Trace：

J = 时间权重 × 整体完成时间 + CPU 调用成本 + NPU 调用成本

J 越低越好。这里的调用成本是赛题规定的计分数值，不等于本机实际占用的 CPU 时间。把每次搬运变快，却增加大量调用，可能反而得分更低。

公开自动评分最多 90 分，另有 10 分设计与可复现性由评委评定。单条输入达到冻结参考成本后，该条优化分封顶；继续降低 J 可以改善同分排序。合法性和资源限制也会影响得分。

## 我们怎样作一次决定

1. **看清当前任务。** 读取可见的未命中请求和运行状态，为目标内存片段建立索引。
2. **生成可行的搬运方案。** 先按容量切分，再把同一张卡上相接或重叠的 SSD 区间组织起来。动态规划比较合并边界及路径。
3. **比较少量完整候选。** 在计算预算允许时，比较不同块长和路径组合，并利用已经到达、尚有任务未完成的批次观察槽位、缓冲池和流水竞争。不会读取后续 Trace。
4. **提交当前决定。** 输出读取、复制及它们的先后依赖。过去已执行的操作不会被改写；窗口内的反事实比较只是帮助选择当前方案。
5. **由模拟器执行并反馈。** 完成时再判断是否值得把这个对象加入缓存。

如果输入包含特别多的内存片段，程序会限制局部模拟的工作量，使用合法的区间规划结果，避免把决策本身变成瓶颈。

## 缓存为什么也可能让结果变差

缓存不是免费的。把一份数据加入 KVCache 池，要额外从 SSD 或 HBM 搬运一次；以后命中缓存，仍需从缓存池复制到目标 HBM。如果加入缓存后再也不用，这次投入就没有回报。

我们的准入规则同时检查：对象是否放得下、是否观察到跨时刻重复访问、最近需求是否仍然新鲜、是否已经缓存或正在提升，以及命中是否比再次前台读取更划算。

后台投入由已经观察到的同键读取工作量形成预算，而不是直接假定未来会复用很多次。实际命中还会反馈到后续预算。对于突然停止的访问或等待很久才完成的任务，新鲜度检查会抑制过时的缓存投入。

这仍是在线预测：相同的前两次访问，后面可能继续访问，也可能立即结束。任何不看未来的策略都无法提前确定是哪种情况。方案通过约束投入降低风险，不承诺每次缓存都能获利。

## 一个容易理解的例子

假设同一张卡收到多份相邻的小读取任务。逐个读取会产生许多命令；合并读取可能减少调用。若目标地址不对齐，程序会比较“临时 HBM 分发”和“DDR 中转”。

如果后面已经到达的批次也在排队，程序会进一步检查：前一种路径是否把任务槽位占满，从而阻塞后面的读取。选择依据是这些可见请求在官方资源规则下的成本，不是输入文件叫什么。

如果某个对象稍后再次出现，程序再结合已观察到的访问节奏和收益预算决定是否缓存；如果它已经很久没有新请求，就不因为历史上重复过而盲目提升。

## 如何判断我们的结论可信

| 要回答的问题 | 包内证据 |
| --- | --- |
| 是否遵守题目规则？ | 官方独立回放、功能回归、边界和变形检查 |
| 是否比官方贪心更好？ | 逐条 J 对照，包含较差的输入，不只展示平均值 |
| 是否只适用于公开题？ | 多种合成分布、冻结后独立家族，以及明确的测试范围说明 |
| 是否能稳定复现？ | 固定源码和输入哈希，每条三次输出哈希核验 |
| 更大数据能否运行？ | 十万请求及高 iov 压力测试，分别记录决策耗时和峰值内存 |

最新数值统一见“05_验证结果/验证报告”，与随包源码哈希对应。公开成绩不能当成隐藏集排名，也不代表真实硬件上的加速比。
