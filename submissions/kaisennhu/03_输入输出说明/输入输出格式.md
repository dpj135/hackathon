# 程序入口与输入输出

提交策略为 `player/solution.cpp`，通过官方 C++17 SDK 的 `create_policy()` 工厂提供 `on_submit()` 与 `on_iocb_complete()` 两个回调。可执行程序使用官方入口加载 JSON Trace、执行策略并保存结果；策略内部不读取未来事件，也不调用模拟器。

## 1. 运行方式

在 `submissions/kaisennhu` 目录运行：

```bash
# 使用随附 Linux x86_64 程序，核验哈希并独立回放
python3 run.py solve --prebuilt \
  --input 04_算法设计与复杂度/示例/相邻对齐小读输入.json --result result.json

# 在其他兼容 Linux 环境，从源码构建再运行
python3 run.py solve \
  --input 04_算法设计与复杂度/示例/相邻对齐小读输入.json --result result.json
```

也可直接调用两个程序：

```bash
02_可执行程序/linux-x86_64/nds_player input.json result.json
02_可执行程序/linux-x86_64/nds_validate input.json result.json
```

参数是输入和输出**文件路径**，不是标准输入协议。成功时退出码为0，完整结果写入输出文件，指标同时打印到stdout；错误写入stderr并返回非零状态。缺少命令行参数返回2，普通输入或执行异常返回1。官方入口另在stderr输出 `NDS_POLICY_PEAK_KB`，单位为KiB。

随附二进制在Ubuntu 24.04、x86_64、glibc 2.39环境构建与验证，动态依赖libstdc++、libgcc、libm和libc；确切环境和哈希见[二进制清单](../02_可执行程序/linux-x86_64/manifest.json)。Windows请使用WSL；其他架构或库版本不兼容时从源码编译。无需GPU、NPU或真实NVMe设备。

## 2. 输入JSON

根对象包含 `instance` 和非空 `events` 数组。完整、可直接运行的输入见[相邻对齐小读](../04_算法设计与复杂度/示例/相邻对齐小读输入.json)；对应[输出](../04_算法设计与复杂度/示例/相邻对齐小读输出.json)的J为6。

| 字段 | 类型与含义 |
| --- | --- |
| `instance.instance_id` | 可选字符串；仅标识输入，不参与选路 |
| `instance.resources` | 正整数资源参数，见下表 |
| `instance.runtime_limits` | 官方资源限制字典；如`max_cpus`、`max_processes`、`max_memory_mb`、`decision_timeout_ms` |
| `instance.fixed_parameters` | 非负整数费用与TTL参数，沿用官方输入 |
| `events[].event` | 固定为`IO_SUBMIT` |
| `events[].time_us` | 非负到达时刻，微秒；事件按时刻非递减排列 |
| `events[].submit.submit_id` | 整条Trace中唯一的非负批次编号 |
| `events[].submit.arrival_us` | 如提供，必须与`time_us`相同；否则沿用事件时刻 |
| `events[].submit.iocbs` | 当前批次1至1024份请求 |

所有地址、长度、编号与时刻均使用SDK的有符号64位整数范围，并须满足其溢出检查。不是所有正整数资源组合都一定存在可执行计划。

| resources字段 | 单位与作用 |
| --- | --- |
| `nvme_bw`、`cpu_copy_bw`、`h2d_bw`、`d2h_bw`、`d2d_bw` | MiB/s，1MiB=2²⁰字节；实际速率还受公开性能表影响 |
| `hbm_capacity`、`ddr_capacity`、`kvcache_pool_capacity` | MiB；分别为临时HBM、DDR和KV缓存池容量 |
| `iocb_capacity` | NDS请求槽位数 |
| `hbm_copy_concurrency`、`h2d_copy_concurrency`、`d2h_copy_concurrency` | 对应复制类型的并发上限 |

SDK兼容旧名`mooncake_capacity`，规范名为`kvcache_pool_capacity`；二者同时出现时必须相等。请求自身的`length`与所有地址/偏移均以**字节**为单位。

费用字段包括`time_cost_per_us`、`promote_ttl_us`，以及`CPU_NDS_FIXED_COST`、`CPU_NDS_PER_CMD_COST`、`CPU_FALLBACK_FIXED_COST`、`CPU_FALLBACK_PER_CMD_COST`、`CPU_PROMOTE_FIXED_COST`、`CPU_PROMOTE_PER_CMD_COST`和CPU/NPU的H2D、D2H、D2D调用费。`promote_ttl_us`以微秒计，其余为模型成本单位。

每个IOCB及其目标iov：

| 字段 | 约束 |
| --- | --- |
| `iocb_id` | 当前批次内唯一的非负编号 |
| `opcode` | 固定为`READV` |
| `device_id` | 目标卡编号，由输入指定 |
| `ssd_offset`、`length` | SSD起点和正长度；范围为左闭右开 |
| `iovs[].iov_id` | 当前IOCB内唯一，可不连续 |
| `iovs[].hbm_addr`、`iovs[].length` | 目标HBM地址与正长度；iov非空且长度之和等于IOCB长度 |

## 3. 输出JSON

根对象由官方入口生成，包含：

| 字段 | 内容 |
| --- | --- |
| `schedule_decisions` | 未命中请求的前台调度决策 |
| `promotion_decisions` | 请求完成后发起的可选PROMOTE；可以为空 |
| `events` | 官方engine生成的执行事件记录 |
| `metrics` | 官方计算的J、历时、调用费、物理字节、命中、提升及延迟等指标 |

前台决策中，`event="SCHEDULE_DECISION"`，`submit_id`匹配批次，`operations`列出操作，`next_wakeup_us=null`。每个operation包含`operation_id`、`path`、`ranges`与`transfers`；中转路径还含`buffer_bytes`。

- `path`为`DIRECT`、`AGGREGATE`或`FALLBACK`。
- `ranges`用`iocb_id / iocb_offset / length`描述本组交付的有效范围，必须精确覆盖相应请求。
- SSD transfer含`transfer_id / type / device_id / physical_ssd_offset / physical_length`；物理起点与长度按512B对齐。
- D2D/H2D transfer用`bytes`及`vectors`描述有效复制；vector含`iocb_id / iov_id / iov_offset / length`。
- `depends_on`保存前置transfer ID，复制依赖本组读取；`group_id`标记同组，`not_before_us`指定最早启动时刻，`priority`为优先级。

PROMOTE决策包含`promote_id`、`source_submit_id`、`source_iocb_id`、`path`、`not_before_us`和`transfer`。`PROMOTE_SSD`通过`SSD_TO_MOONCAKE`读取完整对象；`PROMOTE_HBM`通过D2H搬运已完成对象。缓存命中由框架自动生成H2D，不会作为新的未命中IOCB交给策略。

## 4. 指标与合法性

`metrics.total_cost = time_cost_per_us × trace_time_us + cpu_cost + npu_cost`。`trace_time_us`包含尾部已提交提升；`physical_ssd_bytes`统计真实物理读，`valid_bytes`统计逻辑交付量。`promote_hit_rate`在该SDK中是成功入缓存次数/提升次数，不能当成后续复用命中率。

应以官方validator的独立回放为准，不能只检查输出JSON存在或相信自报metrics。零长度、重复ID、无序时间、目标长度不匹配和非法资源均由SDK拒绝。详细规则和固定版本见[材料来源](../05_自动化测试与复现/依赖来源/材料来源.md)。
