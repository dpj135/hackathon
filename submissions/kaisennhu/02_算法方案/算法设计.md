# 调度算法设计：怎样分组、选路与决定缓存

## 一、先看全貌：两次决策，围绕同一个总成本

**请求到达时，决定“哪些数据一起搬、走哪条路”；请求完成时，决定“是否再搬一份到缓存、从哪里搬”。** 前台负责本次读取，PROMOTE为后续复用付费。程序在线重复这两个决策，只使用已见请求、回调状态及公开费用/性能表；策略内部不调用模拟器、不重放Trace。官方engine只负责外部执行与验证。

一条Trace是一串按时刻到达的读取批次。每份请求IOCB给出SSD区间、目标卡和目标HBM片段（iov）。目标是正确完成全部请求，并最小化：

```text
J = c_t × T + C_CPU + C_NPU
```

c_t是每微秒成本，公开参数为1；T是整条Trace历时，包含尾部已提交PROMOTE；后两项是累计CPU、NPU调用费。**J由官方模拟器实际执行后计算；下文的局部估计只用于选方案，不是评分公式的替代品。** 费用和性能表来自固定官方SDK，详见[入门说明](../00_快速入门/方案介绍.md)。

| 时点 | 框架做什么 | 我们做什么、输出什么 |
| --- | --- | --- |
| 一批请求到达 | 先查KVCache池；命中则自动安排H2D | `on_submit`只收到未命中请求，输出分组、路径、传输项和依赖 |
| 一份请求完整完成 | 触发完成回调 | `on_iocb_complete`返回一条PROMOTE，或不提升 |
| 传输执行与缓存插入 | 排队、共享带宽、释放缓冲；执行TTL与LRU | 读取可见状态，继续下一次决策 |

主流程如下。蓝色步骤由策略决定，灰色步骤由框架执行；不同请求的读取、提升和命中可以交错进行。

## 二、前台：从一批未命中请求得到可执行计划

### 2.1 整理与分块：先定位目标，再从请求头逐块向后切

**整理不搬数据，只建立“请求里的第几个字节，应写到哪块HBM”的索引。** 例如一份6KiB请求有两个iov：前4KiB写到地址A，后2KiB写到地址B。程序记录累计终点[4KiB,6KiB]；逻辑偏移5KiB就对应B＋1KiB。iov是目标片段，不是固定的分块边界：一块可以跨多个iov，一个iov也可以被分成多块。

每份IOCB从请求内偏移o=0开始，依次做下面四步，直到覆盖全部长度：

1. 先取长度l=min（块上限，请求剩余长度）。当前上限2MiB，这是控制规划粒度的人为参数，不是赛题限制，也没有最优性保证。
2. 检查这段能否DIRECT：SSD起点、相关目标地址和每个交集长度都满足512B对齐，则保留l，不受临时池容量限制。
3. 若不能DIRECT，令M=max（临时HBM容量，DDR容量），把l缩至不超过M−（SSD当前起点模512）。这给起点扩读留出空间。若后面还有数据，把块末尾退到512B边界，避免相邻块重复读取边界扇区。末块则保留剩余有效长度，物理读取向外对齐。
4. 记录“所属请求、o、l、能否DIRECT、是否完整请求”；令o←o＋l，继续切下一块。目标映射以后通过索引按交集生成。

为什么用较大池M？这一步只需保证至少有一条中转路径可行；下一步会分别检查AGGREGATE放不放得进HBM、FALLBACK放不放得进DDR。它还没有选定中转路径。

AGGREGATE支持非对齐请求，具体靠“两步搬运”实现：SSD先按512B边界扩读到临时HBM，再用D2D取出有效部分。FALLBACK同样先扩读到DDR，再H2D复制。不能把“允许非对齐请求”理解成“允许非对齐SSD物理命令”。

| 检查对象 | DIRECT | AGGREGATE / FALLBACK |
| --- | --- | --- |
| 请求涉及的源、目标交集地址与长度 | 均须512B对齐 | 可以不对齐 |
| SSD传输项的physical_ssd_offset与physical_length | 须512B对齐 | 也须512B对齐 |
| 中转后的有效数据复制 | 无此阶段 | 可复制非对齐有效范围 |

先区分**请求范围**与**物理读取范围**。从SSD偏移100读取3MiB，逻辑上就是从100开始向后取3MiB，没有把请求改成从0开始：

```text
需要的数据：   [100, 100＋3MiB)
覆盖它的物理读：[0,   3MiB＋512B)
                 ↑首部多读100B；末尾多读412B
```

物理SSD命令要求起点和长度按512B对齐。100不对齐，所以从前一个边界0开始才能覆盖请求；从512开始会漏掉需要的[100,512)这412B。额外字节只存在于物理读取中，复制到目标时跳过它们。**对齐决定补读多少，临时池容量决定分成几块。** 如果容量和候选块上限都足够，也可以考虑一条物理命令覆盖整个范围，仍须对齐。

**实际分块例子：** SSD从偏移100开始读3MiB，目标HBM从一个对齐地址连续存放，临时HBM和DDR都只有1MiB。第一块因源地址不对齐不能DIRECT，缩为1MiB−100B；之后按下表继续：

| 块 | 请求内偏移o | 有效长度l | 物理SSD范围（左闭右开） |
| --- | --- | --- | --- |
| 1 | 0 | 1MiB−100B | [0,1MiB)，首部多读100B |
| 2 | 1MiB−100B | 1MiB | [1MiB,2MiB) |
| 3 | 2MiB−100B | 1MiB | [2MiB,3MiB) |
| 4 | 3MiB−100B | 100B | [3MiB,3MiB＋512B)，只复制有效100B |

四块有效长度之和仍是3MiB，每次临时占用不超过1MiB。第二、三块的SSD起点虽对齐，目标却处在原HBM基址＋o，仍不对齐，因此不能改走DIRECT。这个例子也说明可能留下很小的尾块，程序没有保证消除所有尾块。输入和engine实际输出见[容量分块示例](示例/容量分块输出.json)。

切分结束后，按“卡号、SSD起点、请求编号、片段偏移”排序。**分块只是得到可搬的片段；下面才决定哪些片段合成一组、各组走哪条路。**

### 2.2 枚举分组：哪些片段允许放进同一操作

从排序后每个位置向后扩展，最多看128个片段。扩展中的一组记为G。以下条件全部满足，才继续考虑合并：

| 检查 | 具体规则 | 为什么需要 |
| --- | --- | --- |
| 同卡 | G中所有片段的device_id相同 | 一组传输只发往同一张卡 |
| SSD可连接 | 下个起点向下对齐512B后，不大于当前最远终点向上对齐512B后的值 | 允许相接、重叠及对齐边界内的小间隙，不跨任意大空洞 |
| 块大小 | 合并后的物理SSD范围不超过本次块上限 | 限制单组资源占用 |
| 拆分隔离 | 被拆分的IOCB不与其他IOCB共享操作 | 避免多个操作交叉占用请求槽位造成循环等待 |

对G同时计算两个长度：P是覆盖它的512B对齐物理范围长度；V是各目标有效长度之和。SSD按P读，复制按V搬。若请求重叠，P可能小于V；若需要对齐扩读，P也可能大于V。

随后检查三条路径。**合并不是AGGREGATE专属：三条路径都能服务多个当前请求，但合法条件不同。**

| 路径 | 数据路线 | 额外合法条件 |
| --- | --- | --- |
| DIRECT | SSD→目标HBM | 每个源/目标交集的地址、长度满足512B对齐；逻辑区间连续且不重叠；不同IOCB数不超槽位上限 |
| AGGREGATE | SSD→临时HBM→目标HBM | P不超临时HBM容量；不同IOCB数不超槽位上限 |
| FALLBACK | SSD→DDR→目标HBM | P不超DDR容量；此SDK不占NDS请求槽位 |

不合法的“分组＋路径”直接排除，其余交给成本比较。三条都不可用意味着输入资源下无法生成合法计划，程序报错，不输出缺少覆盖的方案。

### 2.3 估价与动态规划：同时决定分组边界和路径

**估价负责给“这一组走这条路”算预计成本；动态规划负责把各组拼成累计估价最低的方案。** 每个合法候选的估计成本为：

```text
E(G, 路径) = c_t × (t_SSD + t_copy) × m + C_CPU + C_NPU
```

| 参数 | 意义与来源 |
| --- | --- |
| E | 一个分组和路径的预计成本，供规划排序使用 |
| c_t | **每微秒折算多少成本分**，官方`time_cost_per_us`，公开配置为1 |
| t_SSD、t_copy | 物理读取、有效复制的服务时间估值，单位微秒，不含完整队列等待 |
| m | **临时池拥挤惩罚**，我们设置的启发式；DIRECT为1，中转路径为1＋0.5×对应池已用比例 |
| C_CPU、C_NPU | 本组按官方费率计算的调用费，不乘m |

例如服务时间20微秒、调用费5、c_t=1：空池时m=1，E=25；池用了一半时m=1.25，E=30。**m不是官方收费项，0.5不是理论最优权重；最终J不乘m。** 它只让快速规划少选拥挤路径。

公开参数下，一组恰有一读、至多一复制时：

| 路径 | t_SSD依据 | t_copy依据 | CPU＋NPU费 |
| --- | --- | --- | --- |
| DIRECT | P与NDS读取性能表 | 0 | 2＋0＝2 |
| AGGREGATE | P与NDS读取性能表 | V与D2D性能 | 4＋1＝5 |
| FALLBACK | P与DDR读取性能表 | V与H2D性能表 | 11＋1＝12 |

资源工作量按“字节数÷该size、q桶的有效带宽”换算为微秒，不额外除以q。它不是单条传输延迟，也不是整批完成时间的上界。H2D按百分比性能表计算；D2D保留SDK的小块分段公式、绝对带宽表和带宽上限。

先用一维区间DP得到一个快速可行候选：`dp[j] = min(dp[i] + E([i,j), path))`。这里的片段数和卡上请求数只是初步负载代理，不当作最终并发。忙碌或预算不足时保留该候选，避免无界搜索。

**系统空闲时，再采样最终组数cnt，执行“恰好cnt组”的DP。** 此阶段每组恰有一条SSD传输，因此组数等于SSD命令数。n是片段数，h是已经分好的组数：

```text
固定cnt，令SSD估价并发q = active_ssd + cnt
D[0][0] = 0，其余为无穷大
D[h][j] = min(D[h-1][i] + E([i,j), path, cnt))
候选成本 = D[cnt][n]；回溯得到分组和路径
```

copy并发按快速候选中“卡号＋复制类型”的组数比例估计，并受对应并发上限限制。DIRECT不计入copy数量。该估计不跟踪读完、复制启动和提前完成的事件，因此不等于整个执行期的真实并发。

cnt按以下顺序来源去重：快速候选组数、最少可行组数和n；n≤24时尝试全部值，否则取q桶边界、1/2/4/8…几何序列、总字节数除以8KiB至8MiB各倍增尺寸的向下/向上整数。最后在已找到的最佳cnt附近尝试±1、±2、±ceil(5%×cnt)。这些尺寸产生候选，不是固定拆分规则。

**过滤分三层，不能把它们混为一谈：**

| 层次 | 处理 |
| --- | --- |
| 无法合法分组 | 不同卡、空洞、对齐、单组容量、所有者约束先过滤；cnt不在[1,n]、小于最少组数或终态不可达则跳过 |
| 无法同时启动 | 当前有活动/排队/在途提升或旧未完成请求时，不运行计数搜索；重建后，全部NDS所有者必须同时放进槽位，全部HBM/DDR操作缓冲分别不超可用池 |
| 搜索代价过大 | 先算可达状态范围和工作预算，超限跳过该cnt；保留快速候选及已经完成的搜索结果 |

槽位按不同IOCB计数，不按transfer计数。同一IOCB的多条传输可共用槽位，故`cnt > 槽位数`不能直接判非法。不能同时启动的计划仍可能排队合法，只是不进入“以cnt估计初始并发”的搜索族。

启动检查作用于回溯出的最低估价候选；DP没有额外记录每张卡的复制数量和全局池用量，因此可能漏掉同一cnt下另一种可同时启动的划分。这是控制状态规模的取舍。

通过启动检查，只能说明开始时的SSD并发可取cnt；小传输先结束后q仍会下降。当前策略在通过启动检查且完成预算内搜索的候选中，按最小`D[cnt][n]`选定方案；如果没有这样的候选，保留快速区间DP。这里比较的是资源工作量估值，不是最终J；不进行内部模拟来纠正误差。

### 2.4 提交与记账：把计划落实为传输依赖

每组生成一个operation。DIRECT输出一条SSD传输；AGGREGATE/FALLBACK输出一条SSD传输和一条多目标复制，后者的depends_on指向前者。有效数据通过ranges和vectors映射回原IOCB，不会因合并丢失请求边界。

前面3MiB的分块例子，后续规划实际为四块选出AGGREGATE、FALLBACK、FALLBACK、AGGREGATE。它输出四个operation、八个transfer；每块的复制只依赖本块SSD读取，临时池由框架按占用和释放安排周转。最终T=466微秒、CPU=30、NPU=4，J=500。不能把“切成四块”理解为“四块必须同时占住临时池”，也不能理解为“所有块必须走同一路径”。

前台priority=100，最早启动时刻为当前时刻，next_wakeup_us为空。真正何时启动由框架按依赖与资源安排。合并改变传输项数量；并发是某资源上已启动且尚未完成的传输项数量，两者不能混用。

最后仅为**最终选中计划**记账：组内SSD工作、复制工作和调用费按各IOCB有效字节占比分摊，保存到该请求的Work。后台据此估计“缓存命中能替代多少成本”。

## 三、完成后：按四道判断决定是否PROMOTE

PROMOTE是可选缓存投入，不是本次读取的收尾步骤。当前IOCB已经完成，才进入本节；若准入失败，直接返回“不提升”，本次读取仍然成功。

### 3.1 去重与时效：对象是否值得继续评估

缓存键为“卡号、SSD起点、完整长度”，不包含HBM地址。每个键维护访问间隔、最近需求、预算和提升状态。按以下顺序排除不合适对象：

| 判断 | 具体规则 |
| --- | --- |
| 是否由缓存命中完成 | 完成回调中查不到该(submit_id,iocb_id)的arrivals_登记，说明此前未交给on_submit、由框架命中处理；已有该键历史时积累再准入预算，本次不PROMOTE |
| 是否重复投入 | 同键仍在提升，或已经提升且此后没有新的真实未命中证据，则不提升 |
| 对象是否放得下 | 完整对象≤KV池容量 |
| 复用频率检查 | 至少两次可见未命中，且 `0 < gap < TTL`：历史复用间隔短于缓存寿命；同一时刻的重复不形成新的周期证据 |
| 证据新鲜度检查 | `age < TTL` 且 `age ≤ max(1微秒, gap + 2×jitter)`：两个上限取更严格者，避免读取完成时仍按过时需求提升 |

这里保留两类时间信息：**复用频率看历史访问有多密；证据新鲜度看最近需求离现在有多久。** `gap`是该键可见未命中的平滑平均间隔；`age = now − last_arrival`，从该键最近一次可见未命中到达算到当前完成回调，不一定是本次完成请求的等待时长。TTL是缓存寿命参数，实际缓存有效期仍从PROMOTE完成插入起算。

`gap`按“旧值×0.5＋新间隔×0.5”更新；`jitter`按“旧值×0.5＋新间隔偏离旧平均的绝对值×0.5”更新。它是平滑绝对偏差，不是标准差，`2×jitter`不代表统计置信区间。**TTL边界严格排除：`gap = TTL`或`age = TTL`都不通过；只有节奏上限允许相等，且仍须满足`age < TTL`。**

复用字节距离还须≤池容量。它是“该键上次出现后，其他已证明重复的对象累计推进了多少字节”的近似压力指标；单次扫描不推进，重复对象可能重复计入。距离超池容量或两次未命中间隔达到TTL时，清除原复用计数和预算，重新收集证据。

去重无需逐次扫描全部驻留项：索引在途PROMOTE；结束后保持已准入标记。只有**提升已结束之后，框架又把同键作为未命中交给on_submit**，才解除保护。提升期间到达的旧未命中不能触发重复投入。实际命中与失效仍由框架判定；不能用cached_ranges中仍有该键来证明它可命中。

### 3.2 比较来源：这次提升预计花多少成本

先比较PROMOTE_SSD与PROMOTE_HBM的预计就绪成本：SSD看全局读取负载；HBM看源卡D2H活动、在途提升数和并发上限。SSD代价严格更小时选SSD，否则选HBM；D2H并发上限为0时只能选SSD。

来源排序包含共享与排队影响；随后估算该来源的新增服务成本P，供预算判断。P包含PROMOTE固定费80，以及该来源的传输工作量与调用费。**排序用的排队等待不再次逐对象算进P**，避免为同一队列重复记账。精确公式见附录B。

### 3.3 算净收益：未来命中一次是否有用

先定义所需数据，所有时间量均为估值，单位微秒：

| 符号 | 从哪里来 |
| --- | --- |
| R、D | Work中分摊给该请求的SSD、前台复制工作量 |
| C | Work中分摊给该请求的CPU＋NPU调用费 |
| H | 本完整请求缓存命中后的H2D工作量估计 |
| a | 本批该卡有效字节数÷本批全部有效字节数，反映按卡复制的并行范围 |
| g | 提交本批时，最近两个可见on_submit的正到达间隔；未知时为0 |
| E | max（本批全局SSD工作之和＋最忙卡复制工作之和，本请求等待加执行时长） |

若g已知且E<g，节省的服务时间可能被空闲间隔吸收，时间权重w取0；否则w取1。单次命中的净收益估计为：

```text
G = w × c_t × [R + a × (D − H)] + C − C_hit
C_hit = 命中的CPU H2D费 + NPU H2D费 = 2（公开参数）
```

G≤0就不提升。例如稀疏DIRECT的C=2，w=0时G=0；稀疏FALLBACK若独占一组，C=12，仍有G=10的调用费收益。**空闲只折扣时间收益，不抹掉调用费节省。** 最近间隔并不保证未来；整批命中也不进入on_submit，因此这是近似预测。

### 3.4 查预算与容量：有收益，也不能无限投资

预算Q衡量已经观察到的读取支出。对尚未记账的不同到达时刻数m，用当前完成请求的工作估计增加：

```text
Q ← Q + m × max(0, c_t × [R + a × D] + C)
```

同一到达时刻不重复入账；第一轮虽因无复用不准入，第二轮可把此前未记账次数一起计入。它是按当前工作估计外推的历史支出预算，不是预测未来会命中m次。命中完成则增加上次估计的正收益，累计不超过上次提升成本P。

容量压力提高所需预算，但不禁止满池后的热点替换：

```text
门槛 A = P × (1 + max(0, U + F + s − K) / K)
准入条件：G > 0 且 Q ≥ A
```

K是KV池容量，U是框架报告的占用字节（可能含已过期但未回收项），F是本策略已知在途提升字节，s是待提升完整对象大小。对象放不进整个池的情况已在3.1节排除；“超出容量的字节÷K”只是替换压力代理，不是精确计算被驱逐对象的损失。

通过后把Q清零，记录收益和已付成本，输出一条针对当前完整IOCB的PROMOTE：priority=10，not_before_us=当前时刻。这表示允许现在开始，不保证立刻启动，也不保证与前台互不干扰。

提升完成后才能命中；TTL从插入时开始，命中更新LRU但不续TTL。过期后立刻不能命中，却不会在请求到达/完成时从状态删除。当前engine在每次合法插入前清理过期项，再按需要执行LRU。U包含过期残留会使本方案的容量门槛偏保守；它不是有效工作集的精确大小。

## 四、把规则算一遍：何时合并，何时缓存

### 4.1 实际回放：相邻读取不一定应该合并

两个教学输入都只有一批、同卡三个请求、池容量充足，使用公开资源和费用。下表是官方模拟器执行与独立回放结果，输入和当前策略的选中计划保存在[示例目录](示例/)。它们用于解释决策，单独回放，不混入官方评分。

| 输入与候选 | Trace时间T | CPU | NPU | J（c_t=1） |
| --- | --- | --- | --- | --- |
| 三个相邻512B、源目标均对齐：分别DIRECT | 4 | 6 | 0 | 10 |
| 同上：合并DIRECT，实际选中 | 4 | 2 | 0 | **6** |
| 三个相邻4KiB、目标地址不对齐：合并AGGREGATE | 93 | 4 | 1 | 98 |
| 同上：分别AGGREGATE，实际选中 | 33 | 12 | 3 | **48** |
| 同上：合并FALLBACK | 61 | 11 | 1 | 73 |
| 同上：分别FALLBACK | 61 | 33 | 3 | 97 |

第一个输入的三个SSD区间是[0,512)、[512,1024)、[1024,1536)。合并后只有一条1536B DIRECT传输，仍覆盖三份IOCB；时间相同，节省两组调用费，J从10降到6。没有跨时刻重复，完成后不PROMOTE。

第二个输入把长度改为4KiB、目标地址各加1，DIRECT不合法。合并AGGREGATE确实少付10单位调用费，却让一次12KiB D2D替代了三个并行的4KiB D2D：在该性能模型下，T由33增到93，反而多花50单位J。计数DP分别估计不同组数的读取与复制工作量，最终保留三个独立AGGREGATE操作。

本例中，计数DP对cnt=1和cnt=3使用不同的复制并发估计，避免始终用三个复制项的带宽估计合并后的单个复制。表中的实际时间和J由程序外的官方回放得到，不参与在线选路。

可直接复现：

```bash
python3 run.py solve --input 02_算法方案/示例/相邻对齐小读输入.json --result aligned.json
python3 run.py solve --input 02_算法方案/示例/相邻非对齐读取输入.json --result unaligned.json
```

### 4.2 算式示例：有收益，但预算不足时仍不提升

以下是代入公式的教学假设，不是上表实测值：对象已通过复用与新鲜度检查，R=30、D=10、H=12、C=12、a=1、c_t=1；本批E=200，最近提交间隔g=2000，因此w=0。来源比较后P=100。

一次命中的G=0×[30＋10−12]＋12−2=10，确有调用费收益。每次已观察读取提供预算30＋10＋12=52。设K=8MiB、U=7MiB、F=1MiB、s=1MiB，需替换1MiB，门槛A=100×(1＋1/8)=112.5。

| 当前证据 | 预算 | 判定 |
| --- | --- | --- |
| 首次出现 | 不做准入 | 没有跨时刻复用 |
| 第二次完成，把两次尚未记账的观察入账 | 2×52=104 | G虽为正，但104<112.5，不提升 |
| 第三次完成，且需求与工作估值仍相同 | 104＋52=156 | 156≥112.5，提升并把预算清零 |

满池并没有把对象永远挡在外面；更多新鲜复用证据可以支持替换。反过来，若w=0且C=2，则G=0，即使预算充足也不提升。若第三次后不再访问，刚发起的提升仍可能亏损——在线历史不能保证未来收益。

## 五、设计依据与适用边界

| 边界 | 处理方式或限制 |
| --- | --- |
| 对齐、容量、请求槽位与覆盖 | 规划时过滤，官方回放再检查；无法合法完成时明确报错 |
| 无复用、同刻重复、对象过大、TTL/新鲜度不满足 | 不PROMOTE；前台读取照常完成 |
| 满池、热点迁移 | 按替换压力提高预算，允许新热点进入；不精确估计LRU受害者价值 |
| 缓存命中、后台竞争 | 命中仍占H2D并收费；PROMOTE_SSD共享SSD；低优先级不等于资源隔离 |
| 到达突变、尾部提升 | 最近间隔与历史预算可能误判；尾部提升仍进入Trace时间 |
| 大输入与复杂状态 | 搜索有界，超预算保留快速方案；固定q估价不跟踪队列与流水，不能保证全局最优 |

相对官方贪心，变化集中在三个地方：

| 关键观察 | 官方贪心 | 本方案与代价 |
| --- | --- | --- |
| 固定费按操作收，复制性能又依赖块长与并发 | 逐iov选路；对齐走DIRECT，否则按扩读比与容量固定分支 | 联合估计分组和路径；少调用不保证更快，计数搜索有额外开销 |
| 相同逻辑读取有多条合法资源路线 | 路径选择不比较整批竞争 | 保留三条路径，按对齐末端切块；2MiB上限可能错过更有利的块长 |
| 提升先花钱，命中仍需复制；未来不可见 | 同键第二次未命中后尝试一次HBM提升 | 按实际选中计划估算收益，检查复用和预算，再比较来源；仍可能误判热点终止 |

2MiB块上限、128片段窗口、拥挤权重0.5及缓存预测均为启发式。策略适用于题目公开性能模型和回调语义，不保证全局最优；参数与分布变化可能影响效果。成绩和逐例成本见[验证报告](../05_验证结果/验证报告.md)。

## 附录A：实现预算与复杂度

以下数值控制搜索和状态规模。

| 项目 | 当前实现 |
| --- | --- |
| 前台块上限 | 2MiB启发式参数；实际受对齐与池容量约束，不是官方限制 |
| 区间向后搜索窗口 | 最多128个片段 |
| 计数DP规模入口 | 当前请求数不超过1024、iov不超过2048、初始操作数不超过2048 |
| 计数DP入口与边 | 空闲且规模入口满足；n≤16384，合法边≤262144；不满足则保留快速候选 |
| 计数DP预算 | 单次DP≤131072个存储状态；每次on_submit共享2000000次边估价/转移预算；只存可达范围，超限跳过 |
| 访问历史队列 | 最多131072条更新记录 |

计数DP在固定cnt下最坏为O(cnt×B×W)，完整枚举所有cnt仍昂贵。采样之外，实际执行的边估价与转移受共享预算限制；预检查还受状态数、边数和采样规模限制。它是有预算的近似搜索，不保证全局精确。

每次提交预取费率、带宽、容量和池占用，DP内部使用路径枚举，减少重复查表与分配。复制并发按卡和路径计算，计数DP随cnt重新计算；池占用每次回调刷新。

设V为总iov数、B为片段数、W=128、L为最终目标映射交集数。索引构建为O(V)，排序为O(B log B)，区间候选最多O(BW)，所有者集合维护还包含对数因子，映射约为O(B log Vmax + L)。计数DP的预算和预检查开销另计，不能把整个策略简写为O(BW)。

访问历史记录有界，但SDK输入输出、在途请求和缓存状态仍占内存；本方案不声称恒定内存或任意规模安全。

同步R个在途提升约为O(R log(R+1))，另需读取活动传输；策略不逐次遍历全部缓存条目。

## 附录B：来源估价与代码对应

为避免正文被符号打断，PROMOTE来源估价集中列在这里。令f_S为按物理长度和DDR读取性能表得到的SSD服务微秒，f_H为按完整有效长度和复制性能表得到的D2H服务微秒；q_S=全局活动SSD项＋1，至少1；q_H=源卡活动D2H项＋1，受D2H上限L限制，至少1。两项服务估值都使用各自q查桶。n_S、n_H分别是在途SSD提升数、源卡HBM提升数。

```text
SSD来源排序值 = c_t × f_S × q_S × (1 + n_S/q_S) + CPU_PROMOTE_PER_CMD_COST
HBM来源排序值 = c_t × f_H × q_H × (1 + n_H/max(1,L))
                + CPU_D2H_CALL_COST + NPU_D2H_CALL_COST
```

两边共同的固定费80不影响来源排序。选定后，新增投入P按下式计算；a仍为本批源卡字节占比：

```text
选SSD：P = CPU_PROMOTE_FIXED_COST + c_t × f_S + CPU_PROMOTE_PER_CMD_COST
选HBM：P = CPU_PROMOTE_FIXED_COST + c_t × f_H × a
          + CPU_D2H_CALL_COST + NPU_D2H_CALL_COST
```

乘并发数和在途比例是就绪时间代理；P中的a是按卡并行范围的近似权重，都不是官方直接收取的费用。官方只按实际传输执行和固定费率算J。
