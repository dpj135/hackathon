# 时间与空间复杂度

本页按实际代码的开销来源分析；规则与执行门槛见[算法设计](算法设计.md)。候选枚举和快速DP在同一段循环内交织执行，下表分列不表示代码执行两遍。

## 一、符号与搜索范围

| 符号 | 含义 |
| --- | --- |
| s、V、n | 本批IOCB数、iov总数、分块后的片段数 |
| Vmax | 单个IOCB的最多iov数 |
| W | 向后枚举窗口，固定128 |
| B | 存储的合法操作候选数，至多3nW；细化入口上限262144 |
| K、cntₖ | 去重后尝试的组数数量、第k次尝试的总组数 |
| Sₖ | 第k次尝试实际分配的DP状态数，至多131072 |
| A、R | 当前活动传输数、在途PROMOTE数 |
| H、U | 历史记录数、未完成请求数；历史更新队列至多131072条 |
| X、L | 分块对齐检查访问的iov交集次数、最终输出的iov交集数 |

费用与性能表大小固定，单次传输估价为常数次表查找及算术。细化只在系统空闲、本批s≤1024、V≤2048、n≤16384、基础方案操作数≤2048时尝试；还受状态、候选边与工作预算限制。

## 二、前台：快速规划与按需细化

| 开销项 | 时间复杂度 | 主要空间 |
| --- | --- | --- |
| 建立iov索引 | O(V) | O(V) |
| 分块与对齐检查 | O(n log(Vmax+1)+X) | O(n)片段 |
| 片段排序 | O(n log n) | O(n)片段 |
| 候选组枚举与请求去重 | O(nW log(W+1)) | owners集合O(W)；保留候选时另有O(B) |
| 快速DP核心转移 | O(nW) | dp、prev、paths为O(n) |
| 可达性前后缀 | O(n+B) | O(n)，仅细化启用时 |
| 单个cnt的状态构造与预算预检 | 保守O(cnt×n)，含行边界扫描 | O(Sₖ+cnt) |
| 单个cnt的边权重计算 | O(B+n)，按卡状态查表另计 | O(B) |
| 单个cnt的DP核心转移 | O(cnt×B)，下文给出预算约束 | O(Sₖ) |
| 回溯与总资源检查 | O(n log(s+1)+cnt) | 请求所有者集合O(s)、候选计划O(cnt) |
| 最终映射与输出 | O(n log(Vmax+1)+L) | ranges/vectors为O(n+L) |

**快速DP为何是O(nW)：** n个起点，每个最多向后看W个片段，每组比较3条路径，每次状态更新为常数操作。`std::set owners`每次插入最坏O(log(W+1))属于候选组维护，不属于DP状态转移。因此两项相加由O(nW log(W+1))主导；W固定128时，两项都随n线性增长，排序和iov处理另计。X按实际检查次数计，包含重复访问。

此外，回调还会登记历史与未完成请求、同步提升和统计按卡并发。`std::map`、`std::set`查找按对应集合的对数计费；这些开销不能归入DP转移次数。

### 细化的四层循环

```text
for cnt in sampled_counts:
    for h in 0..cnt-1:
        for i in reachable_states[h]:
            for edge in edges[i]:
                update D[h+1][edge.end]
```

`edges[i]`保存以片段i为起点的合法“终点＋路径”操作，`B=Σ_i |edges[i]|`。一层h最多扫描B条边，一个cnt有cnt层，故单个候选的核心转移为O(cnt×B)，最多为O(cnt×nW)。K个候选的未截断上界为`O(B×Σₖcntₖ)`，而不是只扫描K次B。

代码先统计本候选所需工作量，再从每批2000000预算中扣除“边权重计算＋DP转移”。超预算的cnt跳过，已完成的合格方案保留。该预算约束核心估价与转移，不包含全部状态构造、边界扫描、预检查和回溯；总耗时为各项实际开销之和。

**细化空间不会乘K。** 每个cnt的状态和权重在本次求解结束后释放，下一候选复用这一工作阶段；峰值由O(Sₖ+B+n)及当前保留计划组成。快速DP始终只保留一份基础方案；细化每个cnt也只回溯一份最低估价方案。

## 三、后台与跨回调状态

| 开销项 | 时间复杂度 |
| --- | --- |
| 同步在途提升、清理已完成项 | O(R log(R+1)+R log(H+1)) |
| 扫描提升与活动传输 | O(R log(R+1)+A) |
| 查找并清理本次请求状态 | O(log(U+1)+log(H+1)) |
| 来源估价、收益和预算计算 | O(1)，表大小固定 |

一次完成回调的保守时间界为：

```text
O(A + R log(R+1) + R log(H+1) + log(U+1) + log(H+1))
```

后台不遍历全部缓存条目；TTL、LRU和实际命中由框架维护。策略临时集合占O(R)，跨回调持久状态为O(H+U+R)，分别对应History、Work/arrivals和promotions/pending_keys。历史更新队列有固定上限，未完成请求状态在完成回调中释放。

整条Trace的策略时间为全部提交与完成回调耗时之和；策略内存应与框架的输入、运行时状态和输出JSON内存分开统计。

## 四、实测入口

`python3 run.py runtime`使用同一外层计量入口对比本方案与官方贪心；`python3 run.py scale`验证十万请求和高iov输入。39条公开输入的策略回调累计为1.153s、策略堆峰值12.34MiB；时间为逐例三轮中位数之和，内存取正式轮最大值。

复杂度是规模关系，实测秒数不是J中的模拟时间。环境、三轮记录与完整资源结果见[验证报告](../06_性能与资源报告/验证报告.md)。
