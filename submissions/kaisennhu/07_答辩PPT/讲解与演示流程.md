## 请求如何进入DP

先用`IovIndex`定位目标HBM交集，再切成`Piece`。非DIRECT对齐的块受临时池容量限制，内部切点退到扇区边界，减少相邻块的重复扩读；有效请求范围和目标映射不变。随后按卡号、SSD地址排序，只在同卡且物理范围相连的片段间枚举候选组，并检查路径对齐、容量、槽位等约束。

**切块生成规划单位，DP分组选择哪些单位一起搬运。** “按卡分区”体现在排序和禁止跨卡合组，没有额外的分区求解器。AGGREGATE和FALLBACK允许有效范围非对齐，SSD物理读取扩到扇区边界，复制只搬有效字节。具体规则见[算法设计](../04_算法设计与复杂度/算法设计.md)。

## 两页动画如何讲

第4页四次点击：快速规划 → 细化求解 → 执行条件 → 最终选择。

**快速DP输出一份完整基础方案；细化从同一预处理片段列表重新划分，不受快速方案分组边界限制。** 细化对不同总组数分别求解，重估并发，最多每个组数输出一份合格候选，最终只提交一份。

两者体现规划开销与估价精度的权衡。当前实现每批先快速规划；系统忙或规模大时保留快速结果，空闲且规模可控时追加细化。细化的复制并发估计仍引用快速方案的各卡、复制类型比例，基础组数也是采样来源，因此不能描述成完全独立或按规模互斥的两条分支。

| 追问 | 简短回答 |
| --- | --- |
| 细化会不会只能得到原来的解？ | 不会。它从原片段重新分组，增加组数状态并重估边成本，分组与路径都可能改变。 |
| 为什么先快速，不直接细化？ | 以较低开销得到可提交计划和复制分布；当前实现用该分布估计细化候选的复制并发。 |
| 搜索受限怎么办？ | 保留已经完成且通过资源检查的细化候选；没有合格结果就用快速方案。 |

第5页四次点击：排除重复与不可行对象 → 检查复用证据 → 检查净收益 → 检查投入预算。池满允许替换，但替换压力会提高准入门槛。PROMOTE服务未来读取，不是本次读取的必要收尾。

## 性能页的统计口径

39条公开Trace，完整方案相对官方贪心35条更优、4条持平，总J下降36.51%。后台主图双方都正常启用缓存：

| 指标 | 官方贪心 → 本方案 | 口径 |
| --- | ---: | --- |
| 后台总调用费 | 804656 → 41482 | 累计PROMOTE＋命中复制调用费，下降94.84% |
| 每次命中分摊的后台调用费 | 19.71 → 4.94 | 总调用费÷总命中数，下降74.95% |
| 每次提升的平均命中数 | 4.63 → 27.92 | 总命中数÷总提升数，达到6.03倍 |

平均项先汇总再相除，不是逐Trace平均。单次命中固定调用费仍为2，降低的是提升投入的摊销；后台调用费不包含搬运时间费。前后台图表均为完整方案对照，不能将收益独立归因给某个门槛或模块。策略回调时间与含框架执行、输入输出的程序总耗时分别计量。逐例数据与完整结果见[验证报告](../06_性能与资源报告/验证报告.md)。
