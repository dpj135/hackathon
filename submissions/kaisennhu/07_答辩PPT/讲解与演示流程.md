## 两页动画如何讲

第5页五次点击：快速基础方案 → 细化候选 → 入口范围 → 最终选择 → 三个512B片段的结果。**快速DP只输出一份完整方案；细化按多个cnt重新求解，才产生多个完整候选。** 共用的是合法操作集合，不是快速阶段的多份完整方案。

先快速的目的：低成本获得可提交方案和复制分布。仅知道SSD有cnt组，不能直接推出各卡的D2D/H2D并发；当前细化用基础方案的卡号、复制类型比例估计，并把基础组数纳入采样。系统忙、输入超规模或无合格细化结果时保留基础方案。完整转移式、门槛与资源检查见[算法设计1.5节](../04_算法设计与复杂度/算法设计.md#15-联合dp快速规划后按需细化)。

答辩时用一句话概括：**先用低成本规划获得可执行方案和复制分布，再据此追加有限搜索，细化分组与路径。**

| 追问 | 简短回答 |
| --- | --- |
| 为什么先快速，不直接细化？ | 单独假设总组数，还不知道各卡的复制分布。基础方案提供估价依据，同时留下可提交的计划。 |
| 为什么限制搜索？ | 在线调度需要及时给出结果，因此控制候选规模和搜索工作量。 |
| 搜索到上限怎么办？ | 跳过超出预算的候选，保留已完成且通过检查的细化方案；没有合格结果就使用基础方案。 |

具体工程上限留在算法和复杂度文档中，主讲解释控制目的与处理流程；PPT保留教学例子和实测对比数据。

本例两阶段都选一组DIRECT。细化1／2／3组的最低估价E为5.406／7.406／9.406；官方回放中读时间取整为4μs、调用费2，J=6，分别读取时J=10。E是候选排序估价，不是最终J。

第6页五次点击：四道准入判断 → 教学数值例。假设提升投入100、需替换池容量的1/8，门槛112.5；第二次完成预算104，跳过；第三次预算156，提升。该例讲公式，不是实测Trace。

## 性能页的统计口径

39条公开Trace，完整方案相对官方贪心35条更优、4条持平，总J下降36.51%。后台主图双方都正常启用缓存：

| 指标 | 官方贪心 → 本方案 | 口径 |
| --- | ---: | --- |
| 后台总调用费 | 804656 → 41482 | 39条累计PROMOTE＋命中复制调用费，下降94.84% |
| 每次命中分摊的后台调用费 | 19.71 → 4.94 | 总调用费÷总命中数，下降74.95% |
| 每次提升的平均命中数 | 4.63 → 27.92 | 总命中数÷总提升数，达到6.03倍 |

平均项先汇总再相除，不是逐Trace平均。单次命中固定调用费仍为2；降低的是提升投入的摊销。后台调用费不包含搬运时间费。`high_mixed`中双方均无命中，提升3566→0，省去292412提升调用费，是避免无回报投入的直接例子。逐例数据与完整结果见[验证报告](../06_性能与资源报告/验证报告.md)。

## 命令行复现

在材料根目录执行七场景演示，结果写入`运行结果/`：

```bash
python3 run.py demo
```

只复现PPT中的对齐小读：

```bash
python3 run.py solve --prebuilt --input 04_算法设计与复杂度/示例/相邻对齐小读输入.json --result aligned.json
```

随附四组输入输出覆盖对齐合并、非对齐选路、双卡目标与容量分块，可通过`verify_submission.py`统一回放。其余构建、评分和资源测量命令见[复现手册](../05_自动化测试与复现/测试操作手册.md)。
