## 设计依据：先分清观察，再推出设计

第3页标题为“前台联合分组与选路，后台按收益准入”，同时覆盖前后台。按从左到右的顺序讲三条观察：

| 观察 | 关键事实 | 推出的设计 |
| --- | --- | --- |
| 合并有收益，也有代价 | 少付固定费、共享重叠物理读；同时改变并发、块大小和缓冲占用 | 与下一条共同推出联合DP，避免只追求合并 |
| 路径可替代，成本不同 | 同一组可能有多条合法路径，调用费、复制与池需求不同；低成本路径随分组与资源变化 | 每个合法分组比较路径，同时决定边界和路径 |
| 缓存先投入，后回报 | 提升先付费，命中仍需复制；复用不足或证据过时可能无法回本 | 根据复用证据、预计净收益和预算决定是否提升 |

页面用连线把前两条观察汇入前台联合DP，把第三条连接后台准入。先讲这些问题特性，再到后续页面解释实现与公式；不把“合并”和“选路”讲成两个独立的优化模块，也不把预计缓存收益当作保证回本。

## 前台：一条规划流程，两阶段实现

**两阶段都在解决“如何分组、走哪条路径”，不是各自决定一半。** 合并改变并发，并发又影响传输估价；先得到基础方案，再有条件地重新估价和求解。

| 顺序 | 使用什么 | 输出什么 |
| --- | --- | --- |
| 快速DP：每批必做 | 合法分组与路径候选；片段数、卡上请求数作为初始负载代理 | 完整基础方案，以及各卡、各复制类型的组数比例 |
| 细化DP：满足条件才做 | 同一候选集合；采样总组数，结合基础方案的复制分布重估并发 | 重新选择分组与路径；可能与基础方案相同，也可能不同 |
| 提交 | 通过资源检查、完成求解的细化候选中估价最低者；若没有，则保留基础方案 | 一份最终计划，交给engine执行 |

快速状态`dp[j]`表示前j个片段的最低累计估价；一次转移同时选择起点i和路径。细化状态`D[h][j]`增加“已分成h组”，在固定候选总组数下求解。**细化不是只给原方案打分，也不把快速估价和细化估价直接比较。** 它是有预算的并发估价修正，不保证真实J一定优于基础方案，更不保证全Trace最优。

细化入口要求系统无活动传输、排队、在途提升、占槽或旧未完成请求；本批≤1024请求、≤2048 iov、≤16384片段，基础方案≤2048操作。候选边≤262144、单次状态≤131072，每批共享200万次估价／转移预算。每个候选回溯后检查总槽位与临时池容量；无可用细化候选时保留基础方案。

第5页五次点击：

1. **基础方案：** 对合法分组和三条路径做联合DP，获得基础计划及复制分布。
2. **按需细化：** 采样组数，用新的并发假设在同一候选集合上重新求解。
3. **选择输出：** 有可用细化候选则选其最低估价方案，否则保留基础方案。
4. **更新与例子：** 三个同卡、相邻、对齐的512B片段；细化1／2／3组的最低估价分别为5.406／7.406／9.406。两阶段均选择一组DIRECT。
5. **实际结果：** 一条1536B DIRECT、三份请求映射；Trace时间4μs、调用费2，J=6。分别读取时J=10，降低40%。

页面只展示同一细化阶段内的可比估价。完整核验数据：快速阶段SSD／复制并发代理均为3，整组DIRECT／AGGREGATE／FALLBACK估价5.406／32.820／22.559；快速`dp[1/2/3]=3.135/4.271/5.406`。细化根据全DIRECT基础方案估计复制并发为1，整组AGGREGATE估价变为81.648，不能沿用快速数值。代码实际尝试组数顺序1、3、2，页面按升序展示。

估价E是工作量成本，不是实际J。实际读工作3.4059797μs向上取整为4μs；输入、估价和最终输出已核验，见[示例输入](../04_算法设计与复杂度/示例/相邻对齐小读输入.json)与[输出](../04_算法设计与复杂度/示例/相邻对齐小读输出.json)。DP只处理当前未命中的合法连续片段，每起点最多考察128片段；不规划未来，不决定PROMOTE。容量先按单组过滤，细化回溯后再查总量，并非完整的容量状态DP。

## 后台：用更少投入服务有效复用

第6页五次点击依次展开四道准入条件和数值例子。教学假设：提升投入100、需替换池容量的1/8，门槛112.5；第二次完成预算104，跳过；第三次预算156，提升。该例用于讲公式，不是实测Trace。

第11页的两张主图均比较**正常启用缓存的完整方案**，共39条公开Trace，组内共享零点和比例，费用越低越好：

| 指标 | 官方贪心 | 本方案 | 改善 |
| --- | ---: | ---: | ---: |
| 后台总调用费：提升＋命中复制 | 804656 | 41482 | 降低94.84% |
| 每次命中分摊的后台调用费 | 19.71 | 4.94 | 降低74.95% |
| 每次提升的平均命中数 | 4.63 | 27.92 | 达到6.03倍 |

后台总调用费为39条累计值，不含模拟搬运时间费；后两项先汇总再相除，不对逐Trace比值取简单平均。第二项为总调用费÷命中数，将所有提升投入（含无命中投入）分摊到命中请求。**框架对单次命中的固定调用收费仍为2，没有变便宜；降低的是提升投入的摊销。** 第三项是总命中数÷总提升数。两方案分别有8817／301次提升、40831／8403次命中；比值反映完整Trace的投入效率，不代表同尺寸、同缓存内容的受控比较。

直接实例`high_mixed`：双方命中均为0，贪心仍提升3566次，本方案不提升，省去292412提升调用费。全Trace收益还包括前台变化，不全部归因于缓存。

**补充问答：与baseline相比退化，和缓存自身负收益，是两件事。** 公开39条完整方案35胜4平0负。另做各自关闭／启用PROMOTE对照，得到缓存净贡献104909／70205；本方案的命中量和绝对缓存净贡献较小，但投入大幅下降。两条缓存自身略有负收益的输入，完整方案仍优于baseline：

| Trace | baseline J | 本方案开启缓存 J | 本方案关闭缓存 J |
| --- | ---: | ---: | ---: |
| 06_reuse_hot | 41233 | 36356 | 36302 |
| mid_reuse | 185453 | 88409 | 87179 |

两条完整方案分别优于baseline11.83%、52.33%。开关缓存消融包含缓存与前台竞争、选路的联动，不作为上述主图的比较组。公开结果不代表所有负载：扩展292条仍有96条退化，边界与逐例数据见[验证报告](../06_性能与资源报告/验证报告.md)。

## 放映与命令行演示

用PowerPoint放映模式单击或方向键推进。第5、6页各五次原生点击动画；文字、图形和代码均可编辑。放映展示已核验过程，不执行C++。字体为微软雅黑，非Windows环境可能替换字体。

在材料根目录运行七场景演示：

```bash
python3 run.py demo
```

```bash
python3 run.py solve --prebuilt --input 04_算法设计与复杂度/示例/相邻对齐小读输入.json --result aligned.json
python3 run.py solve --prebuilt --input 04_算法设计与复杂度/示例/相邻非对齐读取输入.json --result unaligned.json
```

分别得到合并DIRECT的J=6与分别AGGREGATE的J=48。完整估价、复杂度与缓存公式见[算法设计](../04_算法设计与复杂度/算法设计.md)。
