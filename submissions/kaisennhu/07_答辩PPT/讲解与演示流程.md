## 设计依据：先分清观察，再推出设计

第3页标题为“前台联合分组与选路，后台按收益准入”，同时覆盖前后台。按从左到右的顺序讲三条观察：

| 观察 | 关键事实 | 推出的设计 |
| --- | --- | --- |
| 合并有收益，也有代价 | 少付固定费、共享重叠物理读；同时改变并发、块大小和缓冲占用 | 与下一条共同推出联合DP，避免只追求合并 |
| 路径可替代，成本不同 | 同一组可能有多条合法路径，调用费、复制与池需求不同；低成本路径随分组与资源变化 | 每个合法分组比较路径，同时决定边界和路径 |
| 缓存先投入，后回报 | 提升先付费，命中仍需复制；复用不足或证据过时可能无法回本 | 根据复用证据、预计净收益和预算决定是否提升 |

页面用连线把前两条观察汇入前台联合DP，把第三条连接后台准入。先讲这些问题特性，再到后续页面解释实现与公式；不把“合并”和“选路”讲成两个独立的优化模块，也不把预计缓存收益当作保证回本。

## 前台：一条规划流程，两阶段实现

**两阶段都在解决“如何分组、走哪条路径”，不是各自决定一半。** 合并改变并发，并发又影响传输估价；先得到基础方案，再有条件地重新估价和求解。

**候选操作和完整方案不同：** 合法候选操作是“一组片段＋一条路径”；完整方案由若干操作覆盖全部片段。快速DP虽然比较许多候选操作，最终只输出一份基础方案。细化阶段对多个候选总组数cnt分别求解，才产生多份完整候选；最终仍只提交一份。

| 项目 | 快速DP | 细化DP |
| --- | --- | --- |
| 执行条件 | 每批执行 | 满足空闲、规模与预算条件才尝试 |
| 状态与组数约束 | `dp[j]`：前j段的最低估价，不预先固定组数 | `D[h][j]`：前j段恰好h组；固定cnt后要求最终h=cnt |
| SSD估价并发 | 在途数＋片段数n | 在途数＋cnt；入口空闲，在途数为0 |
| 复制估价并发 | 在途数＋该卡请求数 | 按基础方案的卡号、复制类型比例估计 |
| 输出 | 一份完整基础方案，及其复制分布 | 每个cnt至多一份通过资源检查的完整候选，再选最低估价者 |

快速转移为`dp[j] = min(dp[i] + E(i,j,path))`；细化转移为`D[h][j] = min(D[h-1][i] + E_cnt(i,j,path))`。两者都枚举起点i与路径path；细化增加组数维度，并按cnt重算边权。每个cnt只回溯一个最低估价方案；若资源检查未通过，不为该cnt保留次优方案。没有合格细化候选时使用基础方案。快速E和细化E不直接比较，实际J由官方回放计算。

细化入口要求系统无活动传输、排队、在途提升、占槽或旧未完成请求；本批≤1024请求、≤2048 iov、≤16384片段，基础方案≤2048操作。候选边≤262144、单次状态≤131072，每批共享200万次估价／转移预算。每个候选回溯后检查总槽位与临时池容量；无可用细化候选时保留基础方案。

第5页五次点击：

1. **快速输出：** 一维状态、初步并发估计，产出一份基础方案及复制分布。
2. **细化候选：** 增加组数维度，按每个cnt重估并发，分别求解完整方案。
3. **执行范围：** 展示系统空闲、输入规模、合法边、状态和工作预算的明确门槛。
4. **最终选择：** 细化结果须通过总槽位和临时池检查；无可用结果就保留基础方案。
5. **同一输入：** 三个512B片段，快速选一组DIRECT；细化比较1／2／3组仍选一组，官方J=6。

完整核验数据：快速阶段SSD／复制并发代理均为3，整组DIRECT／AGGREGATE／FALLBACK估价5.406／32.820／22.559；快速`dp[1/2/3]=3.135/4.271/5.406`。细化根据全DIRECT基础方案估计复制并发为1，整组AGGREGATE估价变为81.648，不能沿用快速数值。代码实际尝试组数顺序1、3、2，页面按升序展示。

估价E是工作量成本，不是实际J。实际读工作3.4059797μs向上取整为4μs；输入、估价和最终输出已核验，见[示例输入](../04_算法设计与复杂度/示例/相邻对齐小读输入.json)与[输出](../04_算法设计与复杂度/示例/相邻对齐小读输出.json)。DP只处理当前未命中的合法连续片段，每起点最多考察128片段；不规划未来，不决定PROMOTE。容量先按单组过滤，细化回溯后再查总量，并非完整的容量状态DP。

## 后台：用更少投入服务有效复用

第6页五次点击依次展开四道准入条件和数值例子。教学假设：提升投入100、需替换池容量的1/8，门槛112.5；第二次完成预算104，跳过；第三次预算156，提升。该例用于讲公式，不是实测Trace。

第11页的两张主图均比较**正常启用缓存的完整方案**，共39条公开Trace，组内共享零点和比例，费用越低越好：

| 指标 | 官方贪心 | 本方案 | 改善 |
| --- | ---: | ---: | ---: |
| 后台总调用费：提升＋命中复制 | 804656 | 41482 | 降低94.84% |
| 每次命中分摊的后台调用费 | 19.71 | 4.94 | 降低74.95% |
| 每次提升的平均命中数 | 4.63 | 27.92 | 达到6.03倍 |

后台总调用费为39条累计值，不含模拟搬运时间费；后两项先汇总再相除，不对逐Trace比值取简单平均。第二项为总调用费÷命中数，将所有提升投入（含无命中投入）分摊到命中请求。**框架对单次命中的固定调用收费仍为2，没有变便宜；降低的是提升投入的摊销。** 第三项是总命中数÷总提升数。两方案分别有8817／301次提升、40831／8403次命中；比值反映完整Trace的投入效率，不代表同尺寸、同缓存内容的受控比较。

直接实例`high_mixed`：双方命中均为0，贪心仍提升3566次，本方案不提升，省去292412提升调用费。全Trace收益还包括前台变化，不全部归因于缓存。

完整方案在39条公开Trace中35条更优、4条持平，总J降低36.51%。逐例结果、统计口径与复现方法见[验证报告](../06_性能与资源报告/验证报告.md)。

```bash
python3 run.py demo
```

```bash
python3 run.py solve --prebuilt --input 04_算法设计与复杂度/示例/相邻对齐小读输入.json --result aligned.json
```

分别得到合并DIRECT的J=6与分别AGGREGATE的J=48。完整估价、复杂度与缓存公式见[算法设计](../04_算法设计与复杂度/算法设计.md)。
